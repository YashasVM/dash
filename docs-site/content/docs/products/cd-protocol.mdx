## What it is

This is the wire protocol behind the [`cdx` CLI](./cd-cli): one terminal sender, one browser receiver, and an untrusted Cloudflare relay that introduces them and forwards ciphertext. The file bytes are end-to-end encrypted; the relay never holds the key, the filename, or the file contents.

The companion [cd](./cd) page covers the separate browser-to-browser WebRTC flow. This page covers only the agent path, `cd-transfer-v1`.

## The invitation link

`cdx send <file>` prints one capability URL:

```text
https://cd.yash0.in/s/<transfer-id>#v1.<master-key>
```

- The transfer ID is 16 random bytes, base64url-encoded to 22 characters. It names the relay room and travels in the WebSocket path.
- The master key is 32 random bytes, base64url-encoded to 43 characters. It lives only in the URL fragment, which browsers never send over HTTP or WebSocket.
- The full URL is the receiver credential. Anyone holding it while the sender is online can receive the file, so treat it as a temporary secret.

## Trust model

The relay sees the transfer ID, endpoint addresses, roles, timing, and ciphertext sizes. It never receives the master key, filename, media type, or file bytes. All peer messages are authenticated with AES-256-GCM. The relay can delay, drop, or deny a transfer.

The receiver join token is HKDF-SHA-256 output derived from the master key, the transfer ID salt, and `cd-transfer-v1 receiver join`. The sender registers only the SHA-256 digest of this token, and the browser presents the token when joining. This stops a transfer ID copied from infrastructure logs from occupying the receiver slot. It does not defend against a malicious relay.

The browser trusts the JavaScript served by `cd.yash0.in`; a compromised origin could read the fragment key. This model does not hide traffic metadata, protect a compromised endpoint, or provide resumable or offline storage.

## Relay handshake

Clients connect to `/ws/v1/<transfer-id>` and their first message must be bounded JSON:

```json
{"type":"join","protocol":"cd-transfer-v1","role":"sender","receiverTokenHash":"<base64url>"}
```

```json
{"type":"join","protocol":"cd-transfer-v1","role":"receiver","receiverToken":"<base64url>"}
```

The relay replies with JSON events named `accepted`, `peer-joined`, and `peer-left`. A receiver cannot create a room. Duplicate roles, invalid joins, wrong versions, text frames after admission, and frames above 80 KiB are rejected with stable private WebSocket close codes.

One Durable Object owns one room. Its stored phase and absolute expiry are the source of truth. Rooms admit one sender and one authorized receiver and cannot be reused during their short terminal tombstone lifetime. Ciphertext is forwarded, never stored.

## Encrypted records

After pairing, peers exchange only binary records:

```text
0..1    ASCII "CD"
2       version, 1
3       message kind
4..7    sequence, uint32 big-endian
8..11   plaintext length, uint32 big-endian
12..    AES-GCM ciphertext and 16-byte tag
```

The fixed header and raw transfer ID are AES-GCM additional authenticated data. HKDF derives independent sender and receiver AES keys. The nonce is four fixed direction bytes followed by the uint32 sequence zero-extended to eight bytes. Sequences start at zero in each direction. Reuse, gaps, overflow, unknown kinds, and non-canonical lengths are terminal errors.

Sender kinds are `offer`, `chunk`, and `end`. Receiver kinds are `accept`, `ack`, and `complete`. Offer metadata is encrypted JSON, with the size as a decimal string so Go `uint64` and JavaScript `BigInt` share one exact representation. Chunk content is raw bytes. Ack, end, and complete are fixed binary counters. Either peer closes the socket to abort.

## Flow control and verification

1. The receiver must explicitly accept the decrypted offer before any chunk flows.
2. The sender allows at most 1 MiB of unacknowledged plaintext. An acknowledgement is sent only after the active byte sink owns the bytes.
3. The receiver caps pending encrypted input at 2 MiB and drops peers that ignore flow control.
4. The `end` record authenticates total bytes and chunk count. The receiver compares them against the offer and its own counters before closing its sink, then sends `complete` with matching counters.
5. The sender exits `0` only after receiving that valid `complete`. Per-record authentication, ordered sequences, and authenticated terminal counts detect changed, reordered, duplicated, missing, or extra content without re-reading the file.

## Timeouts and limits

| Parameter | Value |
| --- | --- |
| Sender relay admission | 10 seconds |
| Receiver wait | 15 minutes |
| User consent after offer | 10 minutes |
| Transfer inactivity after acceptance | 45 seconds |
| Hard room lifetime | 2 hours |
| Plaintext chunk | 64 KiB |
| Unacknowledged sender window | 1 MiB |
| Pending receiver ciphertext | 2 MiB |
| Blob fallback | 256 MiB |

The browser reports a Blob result as "ready to download", not "saved". A direct file-system sink reports "saved" only after its writable closes successfully.
